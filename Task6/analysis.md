# Отчёт по результатам анализа Kubernetes Audit Log

audit-extract.json — учебный пример событий, не лог запущенного кластера.

## Подозрительные события

1. Доступ к секретам:

   - Кто: `system:serviceaccount:secure-ops:monitoring`.
   - Где: Secret `example-secret` в namespace `kube-system`.
   - Почему подозрительно: сервис мониторинга пытается прочитать секрет в системном namespace. Получен отказ 403, секрет не прочитан.

2. Привилегированные поды:

   - Кто: `minikube-user`.
   - Комментарий: создал `privileged-pod` в `secure-ops` с `privileged: true`. Ответ 201 подтверждает создание. Такой контейнер получает расширенный доступ к узлу.

3. Использование kubectl exec в чужом поде:

   - Кто: `minikube-user`.
   - Что делал: открыл exec-сессию в `coredns-example` из `kube-system`. Это системный pod, вмешательство может нарушить работу DNS. Какая команда выполнялась, в примере не указано.

4. Создание RoleBinding с правами cluster-admin:

   - Кто: `minikube-user`.
   - К чему привело: создан `escalate-binding` в `secure-ops` со ссылкой на `cluster-admin`. Такая привязка даёт полные права на ресурсы этого namespace, а не всего кластера. Получатель прав в примере не указан.

5. Удаление audit-policy.yaml:

   - Кто: неизвестно, такого события в примере нет.
   - Возможные последствия: отключение аудита мешает расследовать действия в кластере. Но `kubectl delete -f audit-policy.yaml` не удаляет файл на узле и не отключает аудит: Audit Policy не является обычным ресурсом API.

## Вывод

стоит проверить, зачем создавались privileged-pod и привязка к cluster-admin, а также кто использовал exec в системном pod. Лишние права нужно убрать, для мониторинга оставить только необходимые разрешения.

попытка чтения секрета была заблокирована. По этим событиям нельзя подтвердить утечку данных.

для фильтрации реального audit.log из папки Task6:

```bash
python3 filter-audit.py audit.log audit-extract.json
```

нужен Python 3, без дополнительных библиотек. Входной файл — JSON-события по одному на строку. Для поиска privileged и cluster-admin нужен `requestObject` в логе. Изменение файла политики на узле этот фильтр не обнаруживает.
